- write comments compatible with Doxygen, write sparse commants. prefer 1-line. If code line is short and comment is short (re wrapping) then put comment in same line
- do not write comment that explain quite obvious things that code does, write comment when something crucial or complex happens, or when need to explain why it happens

Do defensive programming, write secure code.
Always report speak up about security problems, including not handled age cases.

Always consider known security problems (follow in new code, warn and ask about existing code) also take into account :
- files might be missing, programs might be not compiled, not working, might crash or fail, might also hang
- operations, especially child/parent processes, might crash or migh also hang so also consider some timeouts
- libc, system use, can fail
- files, anon pipes and sockets, web sockets - can be closed, might not work, fail or hang (block)
- avoid programs for hanging forever. Reasonable max timeout should be e.g. 15 seconds. ***
- important: integers can overflow in various ways. even doing range-checks can overflow. Also underflow etc. Also consider unsigned not fitting into signed (for various types).
- always guard arrays, vectors etc against out of bounds access.
- always expect all inputs/data, even from our own files/programs, to be possibly malicious in all possible ways.
- do double checks, e.g. check data on read, but then in following code to use the data still guard against UB, out-of-bounds and such.
- make sure strings are valid, e.g. file names. Guard against extreamly long strings (and also other buffers and memory see magic limits below)
- guard against invalid strings or suspicious, e.g. containing strange characters, control chars, etc. Especially when passing out, passing to system, using as file names.

Limits (the Magical values) :
- TIMEOUT_STANDARD: timeout of operations: usually: 15 second max, 5 seconds normal (warn above).
- TIMEOUT_EXT: 15 seconds max (warn above 5 seconds) - timeout of external programs: but if we wait for external programs, especially when we wait for the node/_serv program to start-up fully.
- TIMEOUT_RPC: when we given a command to node/_serv (e.g. via pipe) then we already given important command which might have critical economical value. Let the task run for even 120 seconds before aborting it (but warn above 5 seconds). Because aborting RPC command that might be blockchain/ecnonomy token in unknown state is very dangerous, log large "WARNING FATAL CRITICAL" and mentiuon aborting RPC command, in such case.
- BUFFER SIZES: strings, rpc commands, files etc. should never exceeed 128 MB of size, warn on seing 10% of that value.
- file names shold not exceed 200 characters (warn on 100) and disallow names that have control chars

If something breaks in our expected chain of communication and execution: can't start program, child/parent dies (before it should) communication with it breakes, can not secure it (close FDs, remove or set ENV, etc) then we MUST ALWAYS abort (and complain loudly) do not ever continue in broken or unknown state.

In fact, probably all errors will result in error_broken, perhaps outside of things left for unit tests where you can use error_broken_or_test.

Error Handling in C++:
- Use throwing exceptions as the primary error handling mechanism for normal operation
- Exceptions should be caught at appropriate levels and handled or re-thrown as needed
- For unit tests and testing code where we must detect failures programmatically, use error_broken_or_test() function instead of direct exceptions
- The error_broken_or_test(test, msg, ...) function:
  - If 'test' parameter is true: throws exception (needed for unit tests to detect failures)
  - If 'test' parameter is false: calls error_broken() to abort program (normal operation)
- Always use RAII and proper exception safety (basic guarantee minimum, strong guarantee preferred)
- Destructors should never throw exceptions
- Use appropriate exception types: std::runtime_error, std::invalid_argument, etc.
- In catch blocks, clean up resources properly before re-throwing or handling
